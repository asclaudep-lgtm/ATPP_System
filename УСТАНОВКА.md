# Установка и развёртывание ATPP_System v6

**Назначение документа.** Этот файл — единая пошаговая инструкция по
развёртыванию системы. Если у Вас один компьютер — пройдите часть **A**.
Если несколько ПК в сети — части **B** (сервер) и **C** (клиенты).
Часть **D** — про резервные копии, **E** — типичные ошибки и решения.

---

## A. Установка на одном ПК (быстрый старт без сервера)

Подходит, если систему пока использует один пользователь и нет необходимости
в сетевой работе.

### A.1. Установить Python

Скачать и установить **Python 3.11** или новее с https://www.python.org/downloads/.

> При установке **обязательно** отметить «**Add Python to PATH**».

Проверить:

```powershell
python --version
```

### A.2. Распаковать ATPP_System

Распаковать `ATPP_System_v6_full.zip` в любую папку, например
`C:\ATPP_System\`. Дальше во всех командах подразумевается этот путь.

### A.3. Установить зависимости

В PowerShell:

```powershell
cd C:\ATPP_System
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Если PowerShell ругается на `Activate.ps1` — выполнить один раз:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

### A.4. Запустить приложение

```powershell
python main.py
```

При первом запуске:
- создастся `data/atpp.db` (SQLite),
- сидируются справочники (материалы, оборудование, профессии, участки),
- создастся пользователь **admin / admin**.

### A.5. Сменить пароль администратора

В приложении: **Сервис → Управление пользователями…** → admin → Сменить пароль.

## B. Серверная часть (одноразово, один ПК-сервер)

Подходит, когда системой пользуется несколько человек одновременно.
Сервер — это обычный Windows-ПК (10/11/Server), который:
- хранит общую базу данных (PostgreSQL 16),
- принимает резервные копии от клиентов,
- сам делает ежедневный бэкап.

### B.1. Подготовить сервер

Сервер должен:
- иметь **статический IP** в LAN (например, 192.168.1.10),
- работать в рабочее время (бэкапы делаются по расписанию),
- иметь свободного места: **минимум 50 ГБ** на диск под БД и бэкапы.

### B.2. Заполнить конфиг сервера

Открыть `scripts\deploy\server_config.ini` в блокноте и заполнить:

```ini
[server]
ip                = 192.168.1.10        # IP этого сервера
lan_cidr          = 192.168.1.0/24      # диапазон LAN, который пускаем к БД

[postgres]
admin_password    = ваш_пароль_postgres ; пароль суперюзера postgres
app_db            = atpp                 ; имя базы для приложения
app_user          = atpp_user            ; имя пользователя приложения
app_password      = СложныйПароль123!    ; пароль приложения (запомнить!)

[backups]
folder            = C:\ATPP_Backups      ; папка-приёмник бэкапов
share_name        = ATPP_Backups         ; имя сетевой шары
keep_daily        = 30                   ; хранить N последних ежедневных
keep_weekly       = 52                   ; и N понедельничных бэкапов
schedule_time     = 23:30                ; время ежедневного бэкапа сервера
```

### B.3. Запустить установку сервера

Открыть PowerShell **от имени Администратора**:

```powershell
cd C:\ATPP_System\scripts\deploy
powershell -ExecutionPolicy Bypass -File .\setup_server.ps1
```

Скрипт автоматически:
1. Установит **PostgreSQL 16** (через Chocolatey либо подскажет ссылку для ручной).
2. Создаст базу `atpp` и пользователя `atpp_user`.
3. Настроит `postgresql.conf` (`listen_addresses = '*'`).
4. Настроит `pg_hba.conf` — пустит на 5432 только указанный диапазон LAN.
5. Откроет порт 5432 в Брандмауэре Windows.
6. Создаст `C:\ATPP_Backups` и расшарит её как `\\<сервер>\ATPP_Backups`.
7. Создаст в Планировщике задач задачу `ATPP_DailyBackup`.
8. Сделает первый тестовый бэкап и проверит подключение.

> Подробности и устранение проблем — в `docs\network_setup_ru.md`, часть A.

### B.4. Запустить приложение на сервере (необязательно)

Если на сервере тоже хотите работать в приложении — повторите шаги
из части C (он же — клиент).

## C. Клиентская часть (на каждом рабочем ПК)

### C.1. Установить Python и распаковать архив

То же, что в A.1 и A.2. Желательно на тот же путь у всех — `C:\ATPP_System\`.

### C.2. Установить зависимости

```powershell
cd C:\ATPP_System
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### C.3. (опционально) Установить PostgreSQL Client Tools

Чтобы клиент мог делать `pg_dump` локальный бэкап — поставить тонкий пакет
**PostgreSQL Client Tools** (`psql`, `pg_dump`, `pg_restore`):

```powershell
winget install --id=PostgreSQL.PostgreSQL.16
```

или вручную с https://www.enterprisedb.com/downloads/postgres-postgresql-downloads
(достаточно отметить «Command Line Tools»).

### C.4. Подключить клиент к серверу

```powershell
cd C:\ATPP_System\scripts\deploy
powershell -ExecutionPolicy Bypass -File .\setup_client.ps1 `
    -ServerHost 192.168.1.10 `
    -AppPassword 'СложныйПароль123!'
```

Скрипт сам:
- проверит, что порт 5432 открыт,
- запишет `data\db.cfg` со строкой подключения,
- запишет `data\backup.cfg` с `\\192.168.1.10\ATPP_Backups`.

### C.5. Первый запуск

```powershell
cd C:\ATPP_System
.\.venv\Scripts\Activate.ps1
python main.py
```

В строке состояния внизу появится зелёная надпись
**«БД: postgres @ 192.168.1.10/atpp»**. Это значит, что клиент подключён
к серверу.

## D. Резервные копии (тройное хранение)

После развёртывания резервные копии создаются **в трёх местах** автоматически:

| Где                                            | Что                              | Когда               |
|------------------------------------------------|----------------------------------|---------------------|
| Сервер: `C:\ATPP_Backups\server\`              | `pg_dump` от Task Scheduler      | каждый день в 23:30 |
| Каждый клиент: `data\backups\`                  | `pg_dump` (или `.db.gz` для SQLite) | при запуске приложения раз в сутки |
| Сервер: `\\<сервер>\ATPP_Backups\<имя_клиента>\` | зеркало бэкапа клиента          | сразу после клиентского бэкапа |

### D.1. Сделать бэкап вручную

В приложении: **Сервис → Резервная копия БД сейчас**.

### D.2. Информация о бэкапах

В приложении: **Сервис → Информация о резервных копиях…** — показывает
последние 10 локальных бэкапов и состояние зеркала.

### D.3. Восстановление при потере сервера

Если сервер сломался, а на нём была актуальная БД:

1. Поднять (восстановить) ОС сервера.
2. Прогнать `setup_server.ps1` заново.
3. Взять самый свежий `*.dump` либо из `C:\ATPP_Backups\server\` (если диск
   уцелел), либо с любого клиента из `data\backups\`, либо с зеркала
   `\\сервер\ATPP_Backups\<любой_клиент>\`.
4. На сервере:

   ```powershell
   cd C:\ATPP_System\scripts\deploy
   powershell -ExecutionPolicy Bypass -File .\restore_db.ps1 -DumpPath "C:\путь\к\atpp_HOST_YYYYMMDD_HHMMSS.dump"
   ```

5. Скрипт сделает страховочный дамп текущей БД, пересоздаст БД и накатит
   указанный дамп.

> Подробные сценарии — в `docs\backup_recovery_ru.md`.

## E. Типичные ошибки

### E.1. «Нет подключения к серверу БД» / «БД: ошибка подключения»

**Причины и проверки:**
- На клиенте файл `data\db.cfg` отсутствует или с ошибкой → проверить.
- IP сервера сменился → исправить в `db.cfg` и `backup.cfg`.
- На сервере выключен PostgreSQL → `services.msc` → служба
  `postgresql-x64-16` запущена.
- Брандмауэр сервера блокирует 5432 → выполнить на сервере:
  ```powershell
  Test-NetConnection 192.168.1.10 -Port 5432
  ```
- Неправильный пароль приложения → переустановить клиент с правильным
  `-AppPassword`.

### E.2. «pg_dump не найден»

**Причина:** на клиенте не установлены PostgreSQL Client Tools (см. C.3).
**Решение:** поставить или сменить БД на SQLite (только для одного ПК).

### E.3. «Не удалось скопировать бэкап на сетевую шару»

**Причина:** SMB-шара недоступна (сервер выключен или нет прав).
**Решение:** само приложение продолжает работать, локальный бэкап в
`data\backups\` создаётся всегда. Проверить:

```powershell
net use \\192.168.1.10\ATPP_Backups
```

### E.4. PowerShell: «не может загрузить файл … запрещено политиками»

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

### E.5. «Ошибка инициализации БД»

При первом запуске БД создаётся автоматически. Если приложение всё же
ругается:
1. Проверить, что в `data\db.cfg` написано без пробелов и опечаток.
2. Удалить `data\atpp.db` если используется SQLite — пересоздаст.
3. Запустить `python main.py` от имени пользователя, у которого есть
   доступ на запись в `data\`.

## F. Обновление до следующей версии

1. Сделать резервную копию (Сервис → Резервная копия БД сейчас).
2. Распаковать новый архив поверх старого с заменой файлов.
3. Активировать venv и установить новые зависимости:
   ```powershell
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```
4. Запустить `python main.py` — лёгкие миграции применяются автоматически.

> При смене мажорной версии PostgreSQL (например, 16 → 17) сначала сделать
> `pg_dump`, потом ставить новую версию, потом `pg_restore`.

## H. Что нового в v6 (по сравнению с v5)

### A. Производство
- **A1.** Справочник производственных участков с CRUD-формой
  («Производство → Участки производства…»).
- **A2.** Возврат партии на доработку (`RouteStepStatus.REWORK`) —
  кнопка «Вернуть на предыдущую операцию».
- **A3.** Отмена наряда из UI с обязательным комментарием.
- **A4.** Печать ярлыков пачкой — единый PDF c сеткой штрих-кодов под
  обычный лазерный принтер.
- **A5.** Прикрепление фотографий к проблеме. Фото копируются в
  `data/issues/<id>/` и автоматически попадают в резервные копии.
- **A6.** In-app уведомления: при назначении проблемы ответственному и
  при её закрытии — открывшему. Меню «Сервис → 🔔 Уведомления»
  (Ctrl+Shift+N).

### B. Отчёты
- **B7.** Выработка за период — кто, на каких участках, годных/брака.
- **B8.** Среднее время прохождения операции по участкам.
- **B9.** Журнал производства за смену.
- **B10.** Аналитика проблем — топ причин простоев, средн. время
  устранения, кол-во блокирующих.
- Все отчёты экспортируются в CSV и Excel («Производство →
  Отчёты производства…»).

### C. Надёжность
- **C11.** Проверка целостности резервных копий
  (`backup.verify_backup_integrity` / `verify_all_backups`).
- **C12.** Алёрт-канал: критические события пишутся в
  `data/alerts.json` и опционально POST-ятся на webhook
  (`data/alerts.cfg` или `ATPP_ALERT_WEBHOOK`). Без внешних зависимостей.
- **C13.** Лог входов/выходов в таблице `user_sessions` (фиксируется
  hostname / app version / время).
- **C14.** Индексы на производственных таблицах для ускорения отчётов.

### D. UX и безопасность
- **D15.** Принудительная смена пароля при первом входе
  (`must_change_password`). Дефолтный admin/admin теперь обязан сменить
  пароль сразу.
- **D16.** Политика паролей — мин. длина, запрет распространённых
  паролей, проверка на совпадение с логином, мин. 2 категории символов.
- **D17.** Тёмная тема (Сервис → Внешний вид…).
- **D18.** Меню «Файл → 🕘 Недавно открытые / ⭐ Избранное» с
  закладками для быстрого возврата к ТП.
- **D19.** Глобальный поиск (F3 или Ctrl+Shift+F) теперь ищет ещё и
  производственные наряды + партии по штрих-коду/serial.

### Требования к БД
Все изменения добавлены через лёгкие миграции в `database/db_manager.py`
— существующая схема обновляется автоматически при первом запуске.
Новые таблицы: `issue_photos`, `notifications`, `user_sessions`,
`user_bookmarks`. Новые колонки: `users.must_change_password`,
`users.password_changed_at`. Новые индексы на `production_events`,
`production_issues`, `route_steps`, `work_order_items`.

Удачного развёртывания.
