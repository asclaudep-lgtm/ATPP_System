# Восстановление ATPP при потере данных

Сценарии: «БД повреждена», «Сервер умер целиком», «Нужно откатиться на вчерашний день».

Все бэкапы — это файлы `atpp_*.dump` (PostgreSQL custom format). Им подходит любой `pg_restore` той же или новой версии PostgreSQL.

---

## Где искать бэкапы (по приоритету)

1. **На сервере** — `D:\ATPP_Backups\server\atpp_server_*.dump`
2. **На сервере, копии от клиентов** — `D:\ATPP_Backups\<имяПК>\atpp_*.dump`
3. **На любом клиентском ПК** — `<папка_проекта>\data\backups\atpp_*.dump`

> Обычно последние 30 дней лежат на сервере, а на каждом клиенте — последние 30 дней его собственных снимков. Поэтому **даже если HDD сервера погиб полностью**, у любого пользователя в `data\backups\` есть свежий `pg_dump`, и из него можно поднять БД заново.

Имя файла включает дату-время: `atpp_<имяПК>_YYYYMMDD_HHMMSS.dump`. Самый свежий по имени — самый новый.

---

## Сценарий 1. Откат БД на конкретную дату

Например, утром обнаружили, что вчера ввели мусор и хотите вернуться к позавчерашнему состоянию.

На сервере:

```powershell
cd C:\ATPP_System\scripts\deploy
powershell -ExecutionPolicy Bypass -File .\restore_db.ps1 `
    -DumpPath D:\ATPP_Backups\server\atpp_server_20260504_230015.dump
```

Скрипт:

1. Сделает «страховочный» дамп текущей БД в `%TEMP%\atpp_pre_restore\` — на случай, если откат вы делаете не туда.
2. Закроет все активные подключения к БД.
3. Пересоздаст БД и наполнит её содержимым выбранного дампа.

Скажите всем пользователям перезапустить ATPP.

---

## Сценарий 2. БД повреждена, серверный диск жив

Те же шаги, что и в сценарии 1 — берите самый свежий `D:\ATPP_Backups\server\atpp_server_*.dump`.

---

## Сценарий 3. Сервер потерян целиком (диск умер / ПК пропал)

1. Найдите подходящую машину под новый сервер (или восстановленный старый). Соблюдайте те же требования, что в `network_setup_ru.md` (Windows 10/11/Server, статический IP).

2. **Найдите свежий `*.dump`**. Возможные источники:
   - резервная копия `\\SERVER\ATPP_Backups\` — но если умер именно сервер, она тоже потеряна;
   - **`data\backups\` на любом клиентском ПК** — это и есть страховка от потери сервера;
   - можно открыть **Сервис → Информация о резервных копиях...** на любом клиенте и увидеть, какие файлы у него есть.

   Скопируйте самый свежий `.dump` на новый сервер, например в `C:\restore\atpp_PC-IVANOV_20260505_091205.dump`.

3. Поднимите PostgreSQL и базу:

   ```powershell
   cd C:\ATPP_System\scripts\deploy
   # Замените значения в server_config.ini под новый сервер (особенно ServerHost!)
   powershell -ExecutionPolicy Bypass -File .\setup_server.ps1
   ```

4. Накатите данные из бэкапа клиента:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\restore_db.ps1 `
       -DumpPath C:\restore\atpp_PC-IVANOV_20260505_091205.dump
   ```

5. Перенастройте клиентов на новый IP сервера (на каждом ПК):

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\setup_client.ps1 `
       -ServerHost <новый_IP> -AppPassword '...'
   ```

   Или просто отредактируйте `data\db.cfg` — поменяйте host:port в строке подключения.

6. Перезапустите ATPP на клиентах. В строке состояния должно быть `БД: postgres @ <новый_IP>/atpp` зелёным.

## Сценарий 4. Восстановление вручную (без скрипта)

Если по какой-то причине не запускается `restore_db.ps1`, то же самое можно сделать руками:

```powershell
$env:PGPASSWORD = 'РодительскийПарольПостгрес!'
psql -h 127.0.0.1 -U postgres -d postgres -c "DROP DATABASE IF EXISTS atpp;"
psql -h 127.0.0.1 -U postgres -d postgres -c "CREATE DATABASE atpp OWNER atpp ENCODING 'UTF8' TEMPLATE template0;"

$env:PGPASSWORD = 'ПарольПриложения!'
pg_restore -h 127.0.0.1 -U atpp -d atpp --no-owner --no-privileges --exit-on-error 'C:\путь\к\atpp_*.dump'
```

## Превентивные привычки

- Раз в месяц проверяйте, что задача `ATPP_DailyBackup` в Task Scheduler действительно отрабатывает (статус «Last Run Result» должен быть `0x0`).
- Раз в полгода проводите учения: возьмите случайный `.dump` и поднимите из него «тестовую БД» (можно с другим именем — `atpp_test`), чтобы убедиться, что бэкапы консистентны.
- Не правьте `data\backups\` на клиентах — оттуда же восстанавливаемся.
- Папку `D:\ATPP_Backups` дополнительно копируйте на внешний носитель/в облако раз в неделю — это защитит от пожара/кражи самого сервера.
