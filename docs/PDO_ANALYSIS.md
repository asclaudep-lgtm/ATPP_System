# Анализ взаимодействия отделов — реальный процесс УЗГА

Дата: 2026-05-14. Источники: `docs/production_ru.md`, RELEASE_v7.md,
MTP_УЗГА_template.xlsx, презентация ATPP_Presentation.pdf.

---

## 1. Реальные роли и их функции

| Роль | Что делает | Где в системе |
|---|---|---|
| **Технолог** | Разрабатывает ТП, утверждает через workflow, передаёт в производство, подписывает МТП | `workflow.py`, `tp_editor.py` |
| **Мастер цеха** | Регистрирует наряд, разбивает на партии, выдаёт штрих-коды, ведёт операции, открывает проблемы | `production.py` |
| **Рабочий** | Стартует/завершает операции, сообщает о проблемах | `production.py` |
| **ОТК** | Приёмка последней операции, контроль качества, открытие проблем | `production.py` |
| **ПДО** (диспетчер) | Принимает заказы, отслеживает сроки, координирует передачу между отделами | ❌ НЕ БЫЛО до v14 |

## 2. Реальный сквозной процесс (как есть в документах)

### Этап 0: Заказ (ПДО — НОВОЕ)
```
Внешний/внутренний заказ → диспетчер ПДО регистрирует ProductionOrder
  ├─ Есть утверждённый ТП? → переходит к Этапу 1
  └─ Нет ТП? → направляет технологу на разработку
```

### Этап 1: Разработка ТП (Технолог)
```
Технолог:
  1. Создаёт ТП (или проверяет существующий)
  2. Добавляет операции, переходы, нормы
  3. Отправляет на согласование (workflow: DRAFT → REVIEW)
  4. Гл.технолог / нормоконтроль / утверждающий ставят подписи
  5. ТП переходит в APPROVED (заблокирован для редактирования)
  6. Технолог подписывает МТП (маршрутно-технологический паспорт)
```

### Этап 2: Передача в производство (Технолог)
```
Технолог:
  1. Открывает утверждённый ТП
  2. «Производство → Передать активный ТП в производство»
  3. Указывает: количество, заказ, приоритет, срок
  4. Создаётся WorkOrder (наряд) в статусе «Передан в производство» (RELEASED)
```

### Этап 3: Регистрация наряда (Мастер цеха)
```
Мастер:
  1. Видит новый наряд в статусе RELEASED
  2. «Регистрация наряда»
  3. Указывает начальный участок
  4. Разбивает на партии: 100 шт → одна партия, 50+50 → две
  5. Система создаёт:
     - WorkOrderItem (партии) — каждой присваивается штрих-код Code128
     - RouteStep (маршрут) — по одной записи на каждую операцию ТП
  6. Наряд → REGISTERED
  7. Печатает ярлыки со штрих-кодами (PNG)
```

### Этап 4: Исполнение (Рабочий / Мастер)
```
Для каждой партии:
  1. Сканируется штрих-код (или вручную)
  2. «Начать операцию» → статус операции «В работе»
  3. «Завершить операцию» → указать годные/брак
  4. Если есть следующая операция → партия передаётся на следующий участок
  5. Если последняя операция → наряд закрывается

Проблемы:
  - Мастер может открыть проблему: нет материала, инструмента, вопрос по КД,
    оборудование, ОТК
  - Блокирующая проблема → наряд ON_HOLD
  - Решение проблемы → наряд возобновляется
```

### Этап 5: Контроль и закрытие (ОТК)
```
ОТК:
  1. Последняя операция → приёмка
  2. Открывает проблемы качества при необходимости
  3. Закрывает наряд: WorkOrder → DONE
  4. Партия → на склад
```

## 3. Что в текущем PDO-модуле сделано НЕПРАВИЛЬНО

| Проблема | Что должно быть |
|---|---|
| `sign_mtp()` просто создаёт запись в БД | Должен генерировать реальный Excel-документ МТП по шаблону УЗГА через `modules/mtp_excel.py` |
| `release_to_shop()` делает handoff запись | Должен вызывать существующий механизм: технолог → `production.release_tech_process()` → создаётся WorkOrder |
| Нет этапа регистрации наряда мастером | Мастер должен разбить наряд на партии через `production.register_work_order()` |
| ПДО создаёт заказ, но не участвует в WorkOrder | ПДО должен быть «надстройкой» над существующим workflow, а не заменой |

## 4. Исправленная схема PDO

```
ProductionOrder (ПДО)                 WorkOrder (Производство)
─────────────────────                 ─────────────────────────
1. ПДО принимает заказ
2. Проверяет наличие ТП
   ├─ Нет → назначает технолога
   └─ Есть → готово
3. Технолог разрабатывает ТП          ─── Технолог передаёт ТП в цех
   и подписывает МТП (Excel)              → создаётся WorkOrder
4. ПДО проверяет готовность           ─── Мастер регистрирует наряд
   (МТП подписан, материал есть)          → партии + штрих-коды
5. ПДО передаёт в цех                 ─── Рабочий выполняет операции
   (handoff + печать документов)          → ОТК принимает
6. ПДО отслеживает сроки              ─── Наряд закрыт
   и эскалирует просрочки
```

**Ключевое:** PDO-модуль — это СЛЕЖЕНИЕ и КООРДИНАЦИЯ. Он не заменяет
существующий производственный процесс, а надстраивается над ним.

## 6. Итог

Реальный процесс УЗГА — это конвейер: **Технолог → Мастер → Рабочий → ОТК**.
ПДО — это диспетчерская надстройка, которая:

- **Принимает заказ** и определяет, есть ли готовый ТП
- **Назначает технолога** если ТП нет
- **Контролирует сроки** на каждом этапе
- **Координирует передачу** документов между отделами
- **Эскалирует** при задержках

ПДО НЕ выполняет технолога, НЕ выполняет мастера, НЕ выполняет ОТК.
ПДО — это «сверху»: видит весь процесс и управляет потоком.
