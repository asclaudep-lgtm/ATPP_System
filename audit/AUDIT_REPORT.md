## ФАЗА 2 — AI-специфические слабости

### 2.1 Галлюцинации API — НАХОДКИ

### [P0] AUDIT-001: `user.set_password()` не существует

**Файл:** `web/auth.py:71` (ИСПРАВЛЕНО в ходе аудита)
**Категория:** Логика / AI-галлюцинация
**Описание:** Метод `set_password()` вызывается на ORM-объекте User, но не определён в модели. Типичная AI-галлюцинация: модель предложила метод, которого нет в кодовой базе.
**Статус:** ✅ Исправлено — заменён на `user.password_hash = db._hash_password(new_pw)`

### [P1] AUDIT-002: PyQt6/PyQt5 enum-несовместимости

**Файл:** `ui/theme.py:466,471`, весь проект
**Категория:** Python / AI-галлюцинация
**Описание:** PyQt6 изменил API enum-ов по сравнению с PyQt5. `Qt.blue` → `Qt.GlobalColor.blue`. AI, обученный на PyQt5-коде, может генерировать неработающие вызовы.
**Влияние:** Потенциальные `AttributeError` при смене темы.
**Исправление:** Провалидировать все обращения к Qt-константам, включить mypy-проверку.

### [P1] AUDIT-003: `FluentIcon` references without validation

**Файл:** `ui/fluent_compat.py:26+`
**Категория:** Python / AI-галлюцинация
**Описание:** `PyQt6-Fluent-Widgets` использует иконки по строковым именам. Нет проверки существования иконки до использования. AI часто генерирует несуществующие имена иконок.
**Влияние:** Пустые/битые иконки в Activity Bar без сообщения об ошибке.
**Исправление:** Добавить try/except с fallback при загрузке каждой иконки (частично сделано в `fluent_compat.py`).

### 2.2 «Выглядит правильно, работает неправильно» — НАХОДКИ

### [P1] AUDIT-004: SQL f-string — потенциальная инъекция

**Файл:** `database/db_manager.py:161`
**Категория:** Безопасность / SQL
**Описание:** `conn.execute(text(f'DROP TABLE "{table_name}"'))` — table_name экранирован кавычками, но источник (`inspect.get_table_names()`) — доверенный. Риск низкий, но паттерн опасен.
**Исправление:** Заменить на параметризованный запрос: `text('DROP TABLE :tbl').bindparams(tbl=table_name)`.

### [P1] AUDIT-005: session.commit() в модулях — ARCHITECTURE VIOLATION

**Файлы:**
- `modules/tp_designer.py:387` — `self.session.commit()` в `create_tech_process()`
- `modules/tp_designer.py:543` — `self.session.commit()` в `update_tech_process()`
- `modules/mes_adapter.py:103` — `session.commit()` в `push_order()`
- `modules/mes_adapter.py:280` — `session.commit()` в `push_work_log()`

**Категория:** Архитектура / Данные
**Описание:** По архитектуре ATPP_System модули бизнес-логики НЕ должны управлять транзакциями. Это обязанность вызывающего кода (UI-виджет, веб-эндпоинт). Текущая реализация создаёт риск **partial commit** — часть данных сохранена, часть нет.
**Воспроизведение:** Вызвать `tp_designer.create_tech_process()` → если `_add_typical_transitions()` упадёт, но `session.commit()` уже вызван в строке 387 → технологический процесс сохранён без переходов.
**Влияние:** Повреждение данных в production.
**Исправление:**
1. Убрать `self.session.commit()` из модулей
2. Обернуть вызовы в `with db_manager.get_session() as s:` в вызывающем коде
3. `tp_designer` должен принимать session параметром, а не хранить свой self.session

### 2.3 Поверхностная обработка ошибок — НАХОДКИ

### [P0] AUDIT-006: 268 except Exception — массовое скрытие ошибок

**Распределение:**
- `ui/widgets/dialog_launchers.py` — 21
- `ui/widgets/tp_editor.py` — 16
- `launcher.py` — 15
- `modules/backup.py` — 14

**Категория:** Архитектура / Надёжность
**Описание:** 268 блоков `except Exception` в 212 файлах. Из них ~62 были `except...pass` (исправлено в ходе аудита на `logger.exception()`), но оставшиеся блоки часто логируют ошибку и продолжают выполнение, маскируя проблемы.
**Пример:** `modules/backup.py:249` — если создание бэкапа упадёт с `except Exception`, оператор не узнает что бэкап не создался.

2. Если ожидаемая ошибка — задокументировать
3. Если неожиданная — пробросить выше или уведомить пользователя

### 2.4 Архитектурные нарушения — НАХОДКИ

### [P0] AUDIT-007: eval() в formula_editor (ИСПРАВЛЕНО)

**Файл:** `ui/widgets/formula_editor.py:307` (ранее)
**Категория:** Безопасность
**Описание:** Пользовательский ввод формул выполнялся через `eval()` с sandbox. Даже с `{'__builtins__': safe_builtins}` это потенциальная RCE.
**Статус:** ✅ Исправлено — заменено на `safe_eval()` на базе `ast.walk()` с whitelist-подходом.

### [P2] AUDIT-008: 95 getattr/setattr вызовов

**Файлы:** Распределены по всей кодовой базе
**Категория:** Архитектура / Читаемость
**Описание:** 95 вызовов `getattr()` / `setattr()` — часть из них динамический доступ к атрибутам моделей, что нормально. Но часть может быть AI-паттерном «доступа к чему угодно без ошибки компиляции».
**Исправление:** Проверить каждый getattr: если имя атрибута известно статически — заменить на прямой доступ.

### 2.5 Заглушки — НАХОДКИ

### [P2] AUDIT-009: 1 NotImplementedError + 96 return None

- `return None` — 96 вхождений. Часть валидны — функции поиска, возвращающие None при отсутствии результата. Но часть могут быть заглушками: «не знаю что вернуть, верну None.»
- `NotImplementedError` — 1. Не критично для сдачи.
- `# TODO / # FIXME / # HACK` — 0. Хорошо, но может означать что известные проблемы не задокументированы.

## ФАЗА 3 — Безопасность

### 3.1 Аутентификация и авторизация

**✅ Хорошо:**
- Пароли хешируются bcrypt (`_hash_password()`)
- JWT с 8-часовым сроком (`web/config.py:18`)
- CORS настроен через env var (не `*`)
- Есть rate limiter (60 запросов/мин/IP)

**❌ Проблемы:**

### [P1] AUDIT-010: JWT secret key leaked to stderr

**Файл:** `web/config.py:13-16`
**Категория:** Безопасность
**Описание:** При отсутствии `ATPP_WEB_SECRET` в окружении генерируется случайный ключ И первые 12 символов выводятся в stderr: `[WARN] ATPP_WEB_SECRET not set — generated random key: mXSSBXMWq_B7...`
**Влияние:** Ключ попадает в логи systemd/docker. Злоумышленник с доступом к логам может подделать JWT.
**Исправление:** Убрать вывод ключа. Выводить только факт генерации: `[WARN] ATPP_WEB_SECRET not set — using auto-generated key`

### [P1] AUDIT-011: JWT в localStorage — XSS риск

**Файл:** `web/frontend/src/App.vue:117,165`
**Категория:** Безопасность
**Описание:** JWT токен хранится в `localStorage`, доступном любому JavaScript на origin. XSS-атака (через вставку скрипта) получит токен.
**Исправление:** Перейти на httpOnly cookie для JWT.

### [P1] AUDIT-012: Пароль возвращался в HTTP-ответе (ИСПРАВЛЕНО)

**Файл:** `web/server.py:89` (ранее)
**Категория:** Безопасность
**Описание:** Endpoint сброса пароля возвращал новый пароль открытым текстом: `{"message": f"Новый пароль: {pwd}", "new_password": pwd}`
**Статус:** ✅ Исправлено — пароль убран из ответа.

### [P2] AUDIT-013: Нет refresh token механизма

**Файл:** `web/auth.py:10-17`
**Описание:** JWT выдаётся на 8 часов без возможности обновления. Если токен украден — злоумышленник имеет 8-часовое окно.
**Исправление:** Добавить refresh token с более коротким TTL для access token.

### 3.2 Инъекции

### [P1] AUDIT-014: text(f'...') — 1 потенциальная SQL-инъекция

**Файл:** `database/db_manager.py:161`
**Описание:** f-строка в сыром SQL. Источник table_name — доверенный (из `inspect.get_table_names()`), но паттерн опасен для copy-paste.

### [P2] AUDIT-015: xml.etree.ElementTree — XML bomb уязвимость

**Файлы:** `modules/onec_exchange.py:65`, `ui/dialogs/onec_import_dialog.py:73`
**Описание:** Парсинг XML без `defusedxml`. При импорте файлов 1C злоумышленник может подсунуть XML-bomb (billion laughs attack).
**Исправление:** Установить `defusedxml` и заменить `ET.parse()` на `defusedxml.ElementTree.parse()`.

### [P2] AUDIT-016: os.startfile() — path traversal в URL

**Файл:** `ui/main_window.py:639`
**Описание:** `os.startfile(url)` с url = "http://localhost:8000" — безопасно. Но функция `_open_web_interface()` не валидирует URL.
**Риск:** Низкий (URL — константа). Но если в будущем URL станет конфигурируемым — риск path traversal.

### 3.3 Секреты в коде

**✅ Проверка пройдена.** Жёстко закодированных паролей/токенов/ключей не найдено. Все секреты — через env vars.

## ФАЗА 4 — Целостность данных и БД

### 4.1 Модели vs миграции

**✅ Хорошо:**
- 68 ORM-моделей в 4 файлах
- Alembic миграции (3 штуки) покрывают основные изменения
- Foreign keys присутствуют на ключевых связях

### [P1] AUDIT-017: `_run_lightweight_migrations()` дублирует Alembic

**Файл:** `database/db_manager.py:67-97`
**Описание:** В коде есть самописная система миграций (`_ensure_primary_keys`, `_ensure_v14_columns`) которая выполняется поверх Alembic. Это дублирование создаёт риск конфликта — Alembic может создать колонку, а `_run_lightweight_migrations()` попытаться создать её снова.
**Исправление:** Всё в Alembic или всё в легковесных миграциях. Не оба.

### [P2] AUDIT-018: Отсутствуют индексы на часто фильтруемые колонки

**Описание:** В коде частые запросы по `product_id`, `tp_id`, `status`, `created_at`. Не все имеют явные индексы в моделях.
**Исправление:** Добавить `Index()` на эти колонки в моделях.

### 4.2 Транзакции

### [P0] AUDIT-019: Длинные транзакции в UI

**Файлы:** Все UI-виджеты с `self.db_manager.get_session()`
**Описание:** UI-виджеты открывают сессию и держат её открытой во время взаимодействия с пользователем. Если пользователь откроет диалог и уйдёт на обед — транзакция висит, блокируя БД.
**Влияние:** Блокировка SQLite (однопоточная запись), таймауты в PostgreSQL.
**Исправление:** Открывать сессию только на время операции: `with db.get_session() as s: result = s.execute(...).fetchall()`. Данные для UI хранить в Python-объектах, не в ORM-сессии.

### [P1] AUDIT-020: StaticPool для SQLite — проблемы concurrency

**Файл:** `database/db_manager.py:31`
**Описание:** `poolclass=StaticPool` + `check_same_thread=False` — все потоки разделяют одно соединение. При конкурентном доступе (веб-сервер + десктоп) возможны `sqlite3.ProgrammingError`.
**Исправление:** Перейти на `NullPool` для SQLite с созданием нового соединения на каждый запрос.

### 4.3 Seed-данные

### [P2] AUDIT-021: Race condition при параллельном создании seed-данных

**Файл:** `database/db_manager.py:200-264`
**Описание:** `_create_initial_data()` проверяет `if session.query(Model).count() == 0:` перед вставкой. При параллельном запуске двух экземпляров возникает race condition — оба увидят 0 и оба вставят данные.
**Исправление:** Использовать `INSERT OR IGNORE` для SQLite или `ON CONFLICT DO NOTHING` для PostgreSQL.

## ФАЗА 5 — UI и UX

### 5.1 Qt-специфические проблемы

### [P1] AUDIT-022: БД в main thread — заморозка UI

**Файлы:** Все UI-виджеты с синхронными запросами к БД
**Описание:** `session.query()` выполняется в главном потоке Qt. При медленном запросе (например, генерация отчёта для 1000+ деталей) UI полностью зависает.
**Воспроизведение:** Нажать «Сгенерировать сводный отчёт» для 1000+ изделий.
**Исправление:** Вынести БД-запросы в `QThread` / `QRunnable`.

### [P2] AUDIT-023: Нет QValidator на числовых полях

**Файлы:** `ui/dialogs/operation_dialog.py`, `ui/dialogs/transition_dialog.py`, многие другие
**Описание:** Поля ввода норм (время, цена, количество) не имеют `QDoubleValidator`. Пользователь может ввести буквы → `float()` → crash.
**Исправление:** Добавить валидаторы на все числовые поля.

### [P2] AUDIT-024: Сигналы без disconnect — утечка памяти

**Файлы:** Динамические виджеты (диалоги, вкладки редактора)
**Описание:** При динамическом создании/удалении виджетов сигналы не отключаются. Это вызывает утечки памяти и «призрачные» вызовы слотов.
**Исправление:** Вызывать `signal.disconnect(slot)` в `closeEvent()` или `__del__()` динамических виджетов.

### 5.2 Пользовательский опыт

### [P2] AUDIT-025: Нет undo после удаления

**Описание:** Удаление изделия или ТП необратимо. Нет undo/восстановления (кроме recycle bin для некоторых объектов).
**Исправление:** Добавить soft-delete с возможностью восстановления.

### [P2] AUDIT-026: Статус-сообщения слишком быстрые

**Файл:** `ui/main_window.py` (statusBar)
**Описание:** Сообщения в statusBar могут исчезать через 2-3 секунды (`showMessage(msg, 3000)`). Длинные сообщения пользователь не успевает прочитать.
**Исправление:** Увеличить таймаут до 5-8 секунд для информационных сообщений.

## ФАЗА 6 — Тесты

### 6.1 Качество тестов

### [P1] AUDIT-027: 126 UI-тестов не проходят

**Расположение:** `tests/test_ui_smoke.py`
**Описание:** Все UI smoke-тесты падают с ошибкой `qt.qpa.plugin: Could not load the Qt platform plugin`. Требуют запущенного X-сервера/дисплея.
**Влияние:** CI не может проверить UI. Регрессии UI не обнаруживаются автоматически.
**Исправление:** Настроить `pytest-qt` с `qtbot` или `xvfb` для headless-тестирования.

### [P1] AUDIT-028: Покрытие UI-слоя 0-30%

**Описание:** Основной UI (`ui/widgets/`, `ui/dialogs/`) практически не покрыт тестами. Любое изменение в UI не имеет автоматической проверки.
**Исправление:** Добавить интеграционные тесты для основных UI-потоков с использованием `pytest-qt`.

### [P2] AUDIT-029: Тесты без assert

**Описание:** Часть тестов (особенно в `test_integration.py`, `test_v7_ui_model.py`) проверяют только что вызов не упал, но не проверяют результат.
**Исправление:** Добавить assert на ожидаемые значения после каждого вызова.

### [P2] AUDIT-030: Seed-зависимость тестов

**Описание:** Тесты полагаются на `_create_initial_data()` в `db_manager.py`. Если seed-данные изменятся — тесты сломаются.
**Исправление:** Использовать фикстуры с изолированными данными для каждого теста.
